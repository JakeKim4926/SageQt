# SageQt 작업 계획 관리

## 목적

3단계 이상으로 나뉘고 여러 세션에 걸치는 작업을 추적한다.
"어디까지 했고, 왜 이 순서이며, 무엇을 의도적으로 남겼는지"를 잃지 않는 것이 전부다.

계획 **내용**은 `docs/decisions/MIGRATION_PLAN.md`에 둔다.
이 skill에는 절차만 둔다. 진행 상황을 skill에 적지 않는다.

## 언제 동작하는가

- 3단계 이상으로 나뉘는 작업을 시작할 때
- Step을 완료했을 때
- 작업 순서나 범위가 바뀔 때
- **프로젝트 규칙(skill)을 수정한 뒤** (아래 *재점검* 참조)
- 중단했던 작업을 다시 시작할 때 — 먼저 계획 문서를 읽는다

다음은 해당하지 않는다.
- 한두 단계로 끝나는 작업
- 버그 수정, 오타 수정, 단일 기능 추가

---

## 계획 문서 구조

`docs/decisions/MIGRATION_PLAN.md`는 아래 순서를 따른다.

```markdown
# <작업명> 계획

## Context
왜 이 작업을 하는가. 문제의 증상이 아니라 원인.

## 진행 상황
| Step | 내용 | 상태 |

### Step 간 의존
왜 이 순서인가. 화살표로 표시.

## 완료된 작업
Step별 결과 요약과 교훈. 체크리스트는 지운다.

## 미해결 리스크
| # | 내용 | 영향 | 대응 |

## Step N — <제목>
브랜치 / 규칙 출처 / 작업 순서(체크박스) / 완료 기준 / 범위 밖 항목

## 검증 방법
```

---

## 작성 규칙

### 완료 기준은 측정 가능해야 한다

"창을 얇게"가 아니라 세어볼 수 있는 문장으로 쓴다.

- 좋음: "SKILL.md가 모두 300줄 이하", "3-OS CI가 모두 통과한다",
  "업무 1종 추가 시 핸들러 파일 1쌍과 등록부 1곳만 바뀐다"
- 나쁨: "구조를 개선한다", "정리한다", "깔끔하게"

### Step 간 의존을 명시한다

순서에 이유가 없으면 나중에 마음대로 바꾸게 된다. 왜 A가 B보다 먼저인지 한 줄로 적는다.

```
1 → 3   폰트 메트릭 차이의 크기가 레이아웃과 디자인 값 설계를 좌우한다
```

### 범위 밖으로 남긴 것과 이유를 적는다

"안 한다"만 적으면 나중에 누락으로 오해한다. 왜 뺐는지가 함께 있어야 한다.

- "`sageqt-ui` 스킬 — Step 1 측정 결과를 반영해야 하므로 Step 3 직전에 작성한다"
- "정적 분석 설정 — CMake · CI와 함께 있어야 검증할 수 있으므로 Step 0에서 한다"

### 리스크는 표로 (내용 / 영향 / 대응)

발견한 위험을 본문에 흩어놓지 않는다. 한 표에 모아야 착수 전에 훑을 수 있다.

### 미검증 커밋을 상단에 표시한다

빌드나 동작 확인을 받지 못한 커밋이 쌓여 있으면 계획 맨 위에 적는다.
다음 작업을 얹으면 실패 원인을 가릴 수 없기 때문이다.

### 조사로 확정한 사실을 적는다

"~일 것이다"가 아니라 실제로 센 숫자와 파일 경로를 적는다.
다음 세션에서 같은 조사를 반복하지 않게 된다.

## 규칙을 고친 뒤에는 계획을 재점검한다 (CRITICAL)

**skill을 수정했으면 계획 전체를 다시 본다.** 현재 Step만 보고 넘어가지 않는다.
규칙이 바뀌면 Step의 내용·순서·존재 이유가 함께 바뀐다.

점검 항목:

- [ ] 바뀐 규칙 때문에 **불필요해진 Step**이 있는가 → 삭제하고 사유를 남긴다
- [ ] 바뀐 규칙 때문에 **순서가 뒤집히는가**
- [ ] 계획에 적힌 **이름·시그니처**가 새 규칙과 맞는가 (네이밍 규약, 반환 규약)
- [ ] 새 규칙이 만든 **모순**이 있는가 (예: 규칙은 A를 금지하는데 계획은 A를 만든다)
- [ ] `DEBT_LOG` 항목의 후속 Step 번호가 여전히 맞는가

계획이 규칙과 어긋난 채로 진행하면, 첫 코드를 쓰는 순간 규칙 위반이 된다.

---

## Step 완료 시

1. 계획 문서의 체크박스를 갱신하고 상태 표를 고친다
2. 완료된 Step의 **상세 체크리스트는 지우고** 결과 요약과 교훈만 남긴다
3. 이번 범위 밖으로 남긴 위험은 `debt-log-guard`로 `docs/DEBT_LOG.md`에 기록한다
4. `git-workflow`대로 `docs/decisions/PR_LOG.md`에 작업을 기록한다
5. 계획 문서 변경은 `docs:` 타입 커밋으로 남긴다

---

## 하지 말 것

- 계획 **내용**을 이 skill에 적지 않는다. 상태는 문서에 둔다
- 완료된 Step의 상세 절차를 문서에 남겨두지 않는다. 문서가 이력서가 되면 현재 할 일이 묻힌다
- 아직 착수하지 않은 Step을 과도하게 상세화하지 않는다.
  앞 Step의 결과가 뒤 Step의 설계를 바꾸는 경우가 많다
- 사용자 확인 없이 Step 순서나 범위를 바꾸지 않는다. 근거를 제시하고 결정을 받는다
