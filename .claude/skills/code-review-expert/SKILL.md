# SageQt Code Review Skill

## 프로젝트 전제

리뷰 전에 반드시 인지한다.

| 항목 | 사실 |
|------|------|
| UI 프레임워크 | Qt 6 Widgets |
| 스타일 | 커스텀 `QStyle` (Fusion 기반 `QProxyStyle`) + `QPalette` — QSS 없음 |
| 빌드 | CMake — 계층마다 타깃 하나, 링크가 의존 방향을 강제 |
| 대상 OS | Windows · macOS · Linux — **코드는 하나, 세팅만 다르다** |
| 저장소 | SQLite — QtSql `QSQLITE` 드라이버 |
| 비동기 | `QtConcurrent::run` + `QFutureWatcher` |
| 웹 UI / QML / 플러그인 / 다국어 | **없음** |

MFC, Win32 메시지, QML, 번역, 플러그인을 전제로 한 지적은 하지 않는다. 이 프로젝트에 없는 개념이다.

## 목적

이 skill은 SageQt의 변경사항을
**기능 동작 여부만이 아니라, 프로젝트 규칙 적합성 / 구조 안정성 / 크로스 플랫폼 동일성 / 확장성 / 유지보수성** 관점에서 검토하기 위한 기준이다.

- 규칙 위반 조기 발견
- 구조 붕괴 방지
- UI / 백그라운드 책임 혼선 방지
- 소유권 누수 · 댕글링 연결 차단
- 한 OS에서만 도는 코드 차단
- 변경 범위 이탈 방지
- 수정 전에 어떤 문제가 핵심인지 우선순위화

이 skill은 "좋다 / 나쁘다" 식의 추상적 평가를 하지 않는다.
반드시 **근거 + 영향 + 수정 방향**으로 말한다.

## 리뷰 기본 원칙

### 1. 먼저 변경 범위를 식별한다

- 어떤 파일이 바뀌었는가
- 신규 파일인지 / 수정 파일인지
- `ui` / `core` / `infra` / `common` / `define` / CMake / 문서 중 어디인지
- 기능 추가인지 / 버그 수정인지 / 리팩토링인지 / 설정 변경인지
- 하나의 목적만 가진 변경인지

변경 범위를 모르고 전체를 추상적으로 평가하지 않는다.

### 2. 관련 skill 기준으로 교차 검토한다

리뷰는 단독 감상평이 아니라, 아래 기준 문서와 대조해서 수행한다.

- `coding-rules` — 네이밍, 타입, 반환 규약, 소유권 규약, 하드코딩 금지, 크로스 플랫폼, 주석 금지, 포맷
- `coding-design` — 폴더 배치, 계층 의존 방향, CMake 타깃, 클래스 분할, 창 비대화, 화면 구성, 스레드 구조
- `git-workflow` — 브랜치 / 커밋 / PR 단위
- `sageqt-plan` — 변경이 진행 중인 주제의 범위에 맞는가, 주제 파일의 *범위 밖* 항목을 건드리지 않았는가
- `debt-log-guard` — 남긴 위험 기록 여부

리뷰 결과에는 "무엇이 문제인지"만이 아니라 "어떤 기준과 충돌하는지"까지 드러나야 한다.

### 3. 심각도 순서로 정리한다

1. Blocker
2. Major
3. Minor
4. Suggestion

사소한 스타일 문제를 치명적 문제보다 앞에 두지 않는다.

### 4. 수정 가능한 형태로 말한다

좋은 리뷰: 문제 지점이 명확하고, 왜 문제인지 설명하고, 영향 범위를 말하고, 수정 방향을 제시한다.

나쁜 리뷰: "구조가 별로다", "좀 더 깔끔하게", "리팩토링 필요", "MVVM으로 바꾸는 게 좋겠다"

### 5. 프로젝트 맥락을 무시하지 않는다

반드시 고려한다.

- 판단의 최종 기준은 `CLAUDE.md`의 *프로젝트 목표*다 — 세 OS에서 같은 코드, 디자인 자유도, 품질 = 일관성
- 세 OS에서 **같은 코드**가 돌아야 한다
- 소유권은 `delete` 없이 **Qt 객체 트리와 `std::unique_ptr`**로 표현한다
- **주석 금지** — 이름으로 의도를 드러내는 코드
- `QString` / Qt 컨테이너 기반
- 헝가리안 없는 Qt 스타일 네이밍 (`m_` 접두사는 유지)
- 워크플로 단위로 기능이 늘어나는 핸들러 확장 패턴
- 계층 규칙을 CMake 링크가 강제하는 구조

즉, "보편적으로 좋아 보이는 코드"가 아니라 **SageQt 규칙에 맞는 코드인지**를 본다.

## 리뷰 절차

## Step 1. 변경 성격 분류

- 기능 추가 (워크플로 추가 / 기존 워크플로 수정)
- 버그 수정
- 리팩토링
- 구조 이동 (파일 배치 / 계층 이동)
- CMake / 빌드 설정 변경
- DB 스키마 / 쿼리 변경
- 화면 / 레이아웃 / 스타일 변경
- 문서 변경

리뷰 결과 첫 줄에서 이 성격을 먼저 밝힌다.

## Step 2. 변경 범위 적절성 확인

- 하나의 변경 목적만 담고 있는가
- 하나의 PR / 브랜치에 너무 많은 관심사가 섞이지 않았는가
- 지금 필요하지 않은 선행 일반화를 하지 않았는가
- 반대로 확장성 고려가 너무 부족하지는 않은가

## Step 3 · Step 4. 규칙 위반과 구조 품질 점검

**리뷰할 때마다 `references/checklists.md`를 읽고** 변경 성격에 해당하는 항목을 점검한다.

| 점검 | 적용 대상 |
|---|---|
| A. coding-rules | 모든 C++ 변경 |
| B. 소유권 | `new` · `connect` · 스레드 경계가 등장하는 변경 |
| C. 크로스 플랫폼 | 모든 변경 |
| D. 계층 의존 | 파일 추가 · 이동 · 삭제, `CMakeLists.txt` 변경 |
| E. 창 비대화 | 창 · 패널 · 다이얼로그 변경 |
| F. DB | Repository · 스키마 · 쿼리 변경 |
| G. 화면 | 위젯 · 스타일 · 표 변경 |
| Step 4. 구조 품질 | 규칙 위반이 없어도 항상 |

## 리뷰 출력 형식

### 1. 총평
변경의 성격과 전체 판단을 2~4문장으로 먼저 정리한다.

### 2. Blocker
반드시 수정해야 하는 문제만 적는다. 각 항목은 **문제 / 왜 문제인지 / 영향 / 수정 방향** 형식을 따른다.

예:
- "`connect(m_watcher, &QFutureWatcher<T>::finished, [this]() { ... })`에 수신 객체가 없다."
- "`coding-rules` 소유권 규약 4와 충돌하고, 패널이 먼저 파괴되면 해제된 `this`로 람다가 실행되어 크래시한다."
- "3번째 인자로 `this`를 넘기거나 멤버 함수 slot으로 바꾼다."

### 3. Major
바로 깨지진 않지만 구조적으로 큰 문제를 적는다.
(계층 책임 혼선, 소유권 규약 이탈, 크로스 플랫폼 위험, 과도한 결합, 창 비대화, 변경 범위 이탈)

### 4. Minor
경미한 개선점을 적는다.
(네이밍 불일치, 파일 배치 어색함, 중복 코드, 상수 분리 필요, 포맷)

### 5. Suggestion
선택적 개선안을 적는다.

### 6. 승인 판단
아래 중 하나로 마무리하고, 반드시 한 줄 이유를 함께 적는다.

- 승인 가능
- 경미 수정 후 승인 가능
- 핵심 수정 후 재검토 필요
- 현재 상태로는 비권장

## 리뷰 시 금지 사항

- 막연한 취향 평가 금지
- 규칙 근거 없는 지적 금지
- 사소한 스타일 지적만 잔뜩 나열 금지
- "다 뜯어고치자" 식의 과도한 재설계 유도 금지
- **이 프로젝트에서 금지된 기법을 대안으로 제시 금지** (`auto`, `delete`, `std::shared_ptr`, `std::unique_ptr<QObject>`, 설명 주석, 플랫폼 분기, `.ui` 파일, QSS · `setStyleSheet`, `SIGNAL()`/`SLOT()`, 싱글턴)
- 존재하지 않는 개념을 전제로 한 지적 금지 (MFC, QML, 번역, 플러그인)
- 문제만 말하고 수정 방향을 주지 않는 리뷰 금지
- 사용자가 요청하지 않은 대규모 코드 재작성 강요 금지

## 우선 검토 포인트 요약

### 최우선
- 람다 `connect`의 수신 객체 누락
- 백그라운드 코드의 위젯 · UI 객체 접근
- UI 스레드 blocking (DB 조회, 문서 생성, `waitForFinished`)
- 플랫폼 분기 · OS API · `\\` 경로
- 창 · 패널에 워크플로 분기 추가
- DB 연결의 스레드 간 공유

### 구조
- `target_link_libraries` 변경
- `CMakeLists.txt` 등록 누락
- 중계 slot
- 화면 클래스의 그리기 · 스타일 · 좌표 코드
- 패널이 표 데이터를 복사 보관 (model · proxy 우회)
- null 계약 위반 (`find*`인데 검사 안 함, 참조여야 할 것이 포인터)

### 데이터
- SQL 문자열이나 QtSql 타입이 Repository 밖으로 유출
- 트랜잭션 경계 불명확
- DB 연결 스코프가 RAII로 닫히지 않음 (`removeDatabase` 누락)

### PR / 브랜치
- 한 PR에 너무 많은 목적 혼합
- 리뷰 불가능한 크기
- 기능 / 버그 / 설정이 한 커밋에 혼재

## 좋은 리뷰 예시 톤

좋은 톤:
- "방향은 맞는데, 현재 구조에서는 패널과 파싱 책임이 섞여서 다음 워크플로 추가 때 문제가 생긴다."
- "지금 당장 blocker는 아니지만, 이미 같은 조건 분기가 두 군데 생겨서 여기서 정리하는 편이 낫다."
- "Windows에서는 대소문자를 무시해서 빌드되지만 Linux에서는 이 include가 깨진다."

피해야 할 톤:
- "그냥 별로다", "너무 더럽다", "다시 짜자", "내 스타일은 아니다"

## 최종 목표

- 위험한 변경은 막고
- 괜찮은 변경은 빠르게 통과시키고
- 애매한 변경은 어디를 고치면 되는지 명확히 보여주고
- 프로젝트 전체 구조를 장기적으로 지키는 것

"지금 돌아가는가"보다 **"이 방식이 다음 워크플로 추가와 세 OS 모두에서 버틸 수 있는가"**를 더 중요하게 본다.
